# ДЗ 4: оптимизация работы СУБД

## 1. Выбранная сущность

Основная сущность: `chat`.

Для нагрузочного сценария используется тип чата `group`.

Почему `group`:

- чат является одной из основных бизнес-сущностей мессенджера;
- сущность создается через публичный API и сохраняется в таблицах `chats` и `chat_members`;
- в отличие от `dialog`, групповой чат не ограничен уникальностью пары пользователей;
- в отличие от `channel`, участники группы в продуктовой модели могут выполнять больше действий с чатом.

## 2. Тестируемые API

Endpoint создания:

```http
POST /api/v1/chats/
```

Тело запроса:

```json
{
  "type": "group",
  "title": "perf-group-000001",
  "members_id": []
}
```

Авторизованный пользователь автоматически добавляется в чат как владелец.

Endpoint чтения:

```http
GET /api/v1/chats/
```

Этот endpoint выбран как основной сценарий чтения, потому что он получает список чатов пользователя и задействует релевантные таблицы чатов. `GET /api/v1/chats/{id}` можно использовать как дополнительный контрольный тест, но он в основном проверяет поиск по primary key и менее интересен с точки зрения оптимизации БД.

## 3. Исходная схема БД

Исходная схема до performance-оптимизаций сохранена в файле:

```text
perf_test/init.sql
```

Все индексы и изменения схемы, добавленные во время оптимизационных итераций, должны быть отдельно задокументированы в этом README и в соответствующем разделе с результатами.

## 4. План тестирования

1. Подготовить чистую БД из `perf_test/init.sql` или из миграций проекта.
2. Запустить приложение на выделенной виртуалке.
3. Создать тестового пользователя и получить auth cookie / CSRF-данные для API-запросов.
4. Запустить нагрузочный тест на создание, чтобы создать 1000 чатов типа `group`.
5. Сохранить результаты создания: общее время, RPS, среднюю задержку, p95, p99, максимальную задержку, долю успешных запросов и ошибки.
6. Запустить нагрузочный тест чтения на `GET /api/v1/chats/`.
7. Сохранить результаты чтения с теми же метриками.
8. Проанализировать узкие места через планы запросов PostgreSQL и метрики приложения.
9. Выполнить оптимизацию только если проблема локальная и исправление выглядит разумным по трудозатратам.
10. Повторить тест чтения после оптимизации и сравнить результаты.

## 5. Политика оптимизации

По условию ДЗ оптимизация выполняется по желанию. Поэтому оптимизируем только в том случае, если измерения покажут понятное и локальное узкое место, например отсутствующий индекс или очевидно неэффективный SQL-запрос.

Если узкое место окажется архитектурным, например API возвращает все 1000 чатов одним ответом без пагинации, это будет зафиксировано как основной вывод. В таком случае корректная оптимизация может требовать пагинации или изменения API, а это уже больше, чем простая настройка БД.

## 6. Артефакты

- `init.sql`: исходный DDL до performance-оптимизаций.
- `scripts/`: скрипты нагрузочного тестирования и вспомогательные скрипты.
- `results/`: сырые отчеты запусков нагрузочных тестов.

## 7. Скрипты запуска

Перед запуском тестов нужно установить `vegeta` на машине, где проводится нагрузочное тестирование.

Для безопасного запуска на выделенной виртуалке добавлен отдельный compose-файл:

```text
perf_test/docker-compose.perf.yaml
```

Он поднимает отдельные контейнеры и отдельные Docker volumes для БД/MinIO. Наружу публикуется только gateway:

```text
8089 -> 8088
```

Такой запуск не должен писать данные в основной контейнер Postgres проекта `2026_1_asap`.

Запуск perf-окружения из корня репозитория:

```bash
docker compose -p asap_perf -f perf_test/docker-compose.perf.yaml up -d --build
```

Проверка:

```bash
docker compose -p asap_perf -f perf_test/docker-compose.perf.yaml ps
```

Остановка perf-окружения без удаления данных:

```bash
docker compose -p asap_perf -f perf_test/docker-compose.perf.yaml down
```

Полное удаление perf-данных после сохранения результатов:

```bash
docker compose -p asap_perf -f perf_test/docker-compose.perf.yaml down -v
```

Базовые переменные окружения:

```bash
export BASE_URL='http://localhost:8089'
```

Если тестовый пользователь еще не создан, его можно создать через API:

```bash
BASE_URL='http://localhost:8089' \
LOGIN='perf_user' \
EMAIL='perf_user@example.com' \
PASSWORD='PerfPass1!' \
perf_test/scripts/register_user.sh
```

Скрипт выведет команды:

```bash
export AUTH_COOKIE='session_id=...'
export CSRF_TOKEN='...'
```

Их нужно выполнить в текущей shell-сессии перед запуском тестов.

Запуск теста создания 1000 групповых чатов:

```bash
COUNT=1000 RATE=20 TIMEOUT=60s perf_test/scripts/run_create.sh
```

Где:

- `COUNT`: сколько чатов нужно создать;
- `RATE`: целевой RPS для создания;
- `TITLE_PREFIX`: префикс названия чатов, по умолчанию `perf-group`;
- `TIMEOUT`: timeout одного запроса, по умолчанию `30s`.

Изначально в задании рассматривался объем 100000 сущностей, но на выделенной виртуалке параллельно работает основной стенд проекта. При попытке запуска 100000 созданий с высоким RPS виртуалка перестала выдерживать нагрузку. После уменьшения объема до 10000 сущностей создание прошло батчами, но чтение списка чатов на заполненной БД привело к timeout и нестабильному состоянию perf-окружения. Поэтому по согласованию объем тестовых данных уменьшен до 1000 сущностей. Это ограничение фиксируется как часть условий эксперимента.

Причина провала чтения на 10000 сущностей: `GET /api/v1/chats/` возвращает весь список чатов пользователя одним ответом без пагинации. Кроме SQL-запроса, обработка каждого элемента списка проходит через бизнес-логику форматирования и проверки подписки, поэтому один HTTP-запрос превращается в тяжелую операцию на уровне БД, gRPC-вызовов, JSON-сериализации и передачи большого ответа.

Запуск теста чтения списка чатов:

```bash
RATE=1 DURATION=30s TIMEOUT=120s perf_test/scripts/run_read.sh
```

Где:

- `RATE`: целевой RPS для чтения;
- `DURATION`: длительность теста;
- `TIMEOUT`: timeout одного запроса, по умолчанию `60s`.

Каждый запуск создает отдельную директорию внутри `perf_test/results/`:

```text
perf_test/results/create_YYYYMMDD_HHMMSS/
perf_test/results/read_YYYYMMDD_HHMMSS/
```

Внутри сохраняются:

- `targets.json`: targets-файл для `vegeta`;
- `result.bin`: бинарный результат `vegeta`;
- `report.txt`: основной текстовый отчет;
- `histogram.txt`: гистограмма задержек.

## 8. Следующие шаги после baseline

После первого прогона нужно перенести ключевые значения из `report.txt` в раздел результатов:

- общее количество запросов;
- успешность;
- RPS / throughput;
- latency avg / p50 / p95 / p99 / max;
- количество ошибок.

Затем для чтения списка чатов нужно снять план SQL-запроса через `EXPLAIN ANALYZE` и решить, есть ли простой кандидат на оптимизацию.

## 9. Условия фактического запуска

Тестирование проводилось на выделенной виртуальной машине, на которой параллельно работал основной стенд проекта. Чтобы не нарушать доступность основного стенда, нагрузка на perf-окружение ограничивалась.

Для изоляции от production-данных использовался отдельный Docker Compose project:

```bash
docker compose -p asap_perf -f perf_test/docker-compose.perf.yaml up -d
```

Проверка изоляции:

- perf-БД: контейнер `asap_perf-db-1`;
- prod-БД: контейнер `2026_1_asap-db-1`;
- после smoke/create тестов в prod-БД не было чатов с префиксом `perf-group-%`.

## 12. Анализ узкого места

Основное узкое место находится в сценарии чтения списка чатов:

```http
GET /api/v1/chats/
```

Причины:

- endpoint возвращает весь список чатов пользователя без пагинации;
- размер JSON-ответа растет вместе с числом чатов;
- на каждый чат выполняется бизнес-логика подготовки ответа;
- при большом количестве чатов один HTTP-запрос становится тяжелой операцией для БД, application layer и JSON-сериализации.

На уровне SQL список чатов выбирается через `chats` и `chat_members`, после чего приложение дополнительно обогащает каждый элемент ответа. Поэтому простое добавление индекса может помочь только частично, но не решает главную проблему полного ответа без ограничения размера.

## 13. Решение по оптимизации

Оптимизация в задании выполняется по желанию. В данном случае основной bottleneck является архитектурным: endpoint списка чатов должен поддерживать пагинацию или cursor-based выдачу.

Рекомендуемая оптимизация:

```http
GET /api/v1/chats/?limit=50&offset=0
```

или cursor-based вариант:

```http
GET /api/v1/chats/?limit=50&before_chat_id=...
```

В рамках текущего ДЗ эта оптимизация не реализовывалась, потому что она меняет контракт API и требует доработки gateway, gRPC-контракта, usecase-слоя, repository-слоя и frontend-клиента. Вместо рискованной правки была задокументирована причина деградации и безопасный предел тестирования на выделенной VM.
